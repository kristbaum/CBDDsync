# Agentic reconciliation of CbDD entities

The sync tool (`uv run sync.py`) lists CbDD entities without a Wikidata item
carrying their deckenmalerei.eu ID (P10626) in `missing/missing_<type>.csv`.
Many of them **do** have a Wikidata item, just without the ID. Your job:
find that item, prove it is the same entity, and write a batch that adds the
ID. You never create items here; entities with no matching item stay in the
report as "no match".

Supported types for now: **people** (`missing/missing_people.csv`, sType
`ACTOR_PERSON`) and **buildings** (`missing/missing_buildings.csv`, sType
`OBJECT_BUILDING`).

## Inputs

- The list to work on: a `missing_<type>.csv` (column `ID`), a range of it, or
  explicit CbDD IDs given by the user. Default batch size: **10 entities** per
  run unless the user says otherwise.
- `sources/entities.json`, `sources/relations.json`, `sources/query.csv`
  (CbDD dump and the current P10626 links). If they are missing, tell the user
  to run `uv run setup.py` and `uv run sync.py` first.
- Wikidata: use the Wikidata MCP tools if available, otherwise the public API
  and SPARQL endpoints (see "Wikidata lookups").

## Outputs

Two files per run in `agentic-reconcile/to_match/`, same base name
`<type>_<YYYY-MM-DD>` (add `_2`, `_3` … if it already exists):

1. `<base>.qs`: QuickStatements 3.0 batch, V1 commands, one line per **confirmed**
   match:

   ```
   Q<matched item>	P10626	"<CbDD ID>"
   ```

   TAB-separated, QID first, the CbDD ID quoted. No `+` prefix (adding the
   same ID twice is then a no-op), no `CREATE`, nothing else. Only matches with
   confidence **high** go in here.
2. `<base>.md`: the report (format below), covering **every** entity of the
   run, including rejected and ambiguous ones.

Never edit files in `missing/` or `existing/`; they are regenerated by
`sync.py`.

## Workflow

### 1. Pick the entities and build dossiers

```bash
python3 agentic-reconcile/scripts/cbdd_context.py \
    --csv missing/missing_people.csv --limit 10 --skip-done
```

`--skip-done` drops IDs already present in any file in `to_match/`, so
consecutive runs continue where the last one stopped. Use `--offset` to pick
another slice, or pass IDs directly as arguments.

The dossier collects what the CbDD dump knows about each entity:

- **People:** name and alternative names, gender, GND ID, every work they are
  related to with the **role** (`PAINTERS`, `PLASTERERS`, `ARCHITECTS`,
  `COMMISSIONERS`, `TEMPLATE_PROVIDERS`, …), the work's dating, host building
  and place, an approximate activity period, co-workers (with their QIDs if
  they are on Wikidata), and passages of the CbDD articles that mention the
  person. The texts often give life dates ("Joseph Anton Reiser (1757–1805)"),
  origin ("einer Gammertinger Malerfamilie") or office ("Bauinspektor").
- **Buildings:** address, coordinates, dating, functions, condition,
  GND ID, Bildindex object number (→ P2092), the ensemble it belongs to, its
  rooms, the people involved, the CbDD summary text.

If something in the dossier is unclear, read the raw records in
`sources/entities.json` / `sources/relations.json` (relations are stored in
both directions; `ID -> relTar` with `sType` as the role, e.g. a painting
`PAINTERS ->` a person).

### 2. Find candidates

Try the strongest key first and stop searching once it hits:

1. **GND ID** (people and buildings): an item with `P227` = the CbDD GND ID.
   This is the best key, but still verify it (step 3); CbDD has a few
   malformed GND values (wrong length, missing check digit).
2. **People:** search by name. CbDD writes "Surname, Given names"; search
   "Given Surname" and the surname alone, in German. Try spelling variants
   (Joseph/Josef, Johann/Joh., ph/f, Italian and Latin forms,
   "von"/"de"), and the alternative names. Look at every candidate that is a
   human (`P31 Q5`).
3. **Buildings:** search items within ~300 m of the coordinates, then by name
   and locality. CbDD names are "Locality, Building" ("Polling, ehem.
   Augustiner-Chorherrenstift, Studienseminar").

Use the co-workers and buildings that already have QIDs: a candidate whose
item links to them (e.g. it is the `P170` creator of a painting in the same
building, or its article names the same church) is a strong hint.

### 3. Check each candidate against the CbDD evidence

Fetch the candidate's statements and compare. Write down every check, passed
or failed; the report needs them.

**People**

| Check | Wikidata | CbDD evidence | Rule |
|---|---|---|---|
| Lifetime vs. works | `P569` birth, `P570` death, `P1317` floruit, `P2031`/`P2032` work period | dating of works in roles where the person must be alive | Born at least ~12 years before their first work (≈20 for architects/master builders); died no earlier than ~2 years before their last work. An artist on an 18th-century painting cannot be born after 1900. |
| Exempt roles | | `TEMPLATE_PROVIDERS`, `REFERENCE_PERSONS`, `DONORS` | Templates are often engravings decades or centuries older; depicted/referenced persons can be long dead. Do **not** apply the lifetime rule to these roles; instead the person should have lived *before* the work. |
| Commissioners | | `COMMISSIONERS` | Often nobles, abbots, abbesses, prince-bishops. They may have commissioned as minors (regency) or died before completion; allow more slack, but the office must fit the place and time (a prince-abbess of Buchau, an abbot of the monastery the work is in). |
| Occupation | `P106` | the role | `PAINTERS` → painter, fresco painter; `PLASTERERS` → stuccoist; `ARCHITECTS`/`BUILDERS` → architect, master builder; `SCULPTORS` → sculptor. A missing occupation is not a contradiction; an incompatible one is. |
| Place | `P19`, `P20`, `P937`, `P27` | places of work | Should be plausible: same region, or a known itinerant artist. A painter who never left Italy, working only in Bavaria per CbDD, is suspicious. |
| Gender | `P21` | `gender` | Must match. |
| Text facts | descriptions, sitelinks | CbDD text passages | Life dates, family, offices in the CbDD text must agree. |
| Already linked | `P10626` on the candidate | | If the candidate already has a **different** P10626, do not match: report it as a possible CbDD duplicate. |

**Buildings**

| Check | Wikidata | CbDD evidence | Rule |
|---|---|---|---|
| Location | `P625` | coordinates | Within ~300 m (large complexes more). |
| Locality | `P131`, `P281`, `P6375` | `addressLocality`, `addressZip`, `addressStreet` | Must agree. |
| Scope | `P31`, `P361`/`P527` | name, functions, "Part of", parts | Same *scope*: the CbDD building "Kloster X, Bibliothek" is not the Wikidata item for the whole monastery, and a church is not its monastery. If CbDD has the part and Wikidata only the whole, that is **no match**. |
| Identity over time | `P571`, `P576`, `P5816` | dating, condition | A destroyed and rebuilt building may have separate items for the old and new building; match the one CbDD describes (CbDD documents the baroque interiors). |
| Identifiers | `P227`, `P2092` (Bildindex object number, the digits of `obj…`), `P4244` (Bavarian monument ID) | normdata | Any matching identifier is strong evidence. |
| Already linked | `P10626` | | As for people. Also see `errors/duplicates.md`. |

### 4. Decide

- **high**: a matching GND (or Bildindex) ID with no contradiction, **or** at
  least two independent agreeing hints (e.g. name + lifetime fits the works +
  occupation; coordinates + name + locality) with no contradiction, and no
  second candidate that fits as well. → `.qs` line and report.
- **medium**: plausible but thin (name and period fit, nothing else
  confirms), or two candidates not fully separable. → report only, with what
  would settle it.
- **no match**: no candidate, or all candidates contradicted. → report only.

One contradiction (wrong lifetime, wrong gender, different P10626, wrong
scope) rules a candidate out, however good the name match. Never put two CbDD
IDs on the same QID in one batch, and never one CbDD ID on two QIDs. If both
come up, downgrade them to medium and explain.

Do not guess. Every claim in the report must come from the dossier, the
source JSON, or a statement/page you actually looked up.

### 5. Write the files

Write the `.qs` (high matches only) and the `.md` (all entities), then run a
self-check:

- every `.qs` line has 3 TAB-separated fields, a QID, `P10626` and a quoted
  UUID that appears in the report as **high**;
- no QID and no UUID occurs twice in the `.qs`;
- none of the QIDs already has a P10626 on Wikidata (re-check right before
  writing; `sources/query.csv` may be stale).

Finish with a short summary to the user: counts per decision and the two file
paths. Do not run the batch; the user reviews and runs it.

## Report format (`<base>.md`)

```markdown
# CbDD → Wikidata matches: <type>, <date>

Input: `missing/missing_<type>.csv`, rows <offset>–<offset+n> (or: IDs given by the user).
Batch: `<base>.qs`, <n> commands. High: <n>, medium: <n>, no match: <n>.

## Matched (high)

### <CbDD name> → <Wikidata label> (Q…)

CbDD: https://www.deckenmalerei.eu/<ID> · Wikidata: https://www.wikidata.org/wiki/Q…

| Evidence | CbDD | Wikidata | Result |
|---|---|---|---|
| GND | <GND> | P227 <GND> | match |
| Lifetime vs. works | PAINTERS, works 1776–1790 | P569 1757, P570 1805 | fits |
| Occupation | PAINTERS | P106 painter | fits |
| Place | Gammertingen, Bad Buchau | P19 <place> | fits |
| CbDD text | "… (1757–1805) … einer Gammertinger Malerfamilie" | | agrees |

Rejected candidates: Q… (born 1902, after the works).

## Uncertain (medium), not in the batch

### <CbDD name>
Candidates: Q… (why it fits, what is missing), Q… (…).
Would settle it: …

## No match

- <CbDD name> (<ID>): searched "…", "…"; candidates Q… (rejected: …). Probably no item yet.

## Notes

- Data issues found in CbDD (malformed GND, wrong dating, suspected duplicates).
- Additions the matched items could use (e.g. GND missing on Wikidata).
```

Leave out empty sections.

## Wikidata lookups

With the Wikidata MCP server: `search_items` for names, `get_statements` for a
candidate, `execute_sparql` for the queries below. Without it, use the HTTP
endpoints and send a descriptive `User-Agent`:

- Name search: `https://www.wikidata.org/w/api.php?action=wbsearchentities&search=<name>&language=de&uselang=de&type=item&limit=20&format=json`
- Exact identifier: `https://www.wikidata.org/w/api.php?action=query&list=search&srsearch=haswbstatement:P227=<GND>&format=json`
- Full item: `https://www.wikidata.org/wiki/Special:EntityData/<QID>.json`
- SPARQL: `https://query.wikidata.org/sparql?format=json&query=…` (WDQS; needed
  for `wikibase:around`). QLever (`https://qlever.dev/api/wikidata`) is
  faster for plain lookups but has no label or geo services.

People with this GND, with dates and any existing CbDD ID:

```sparql
SELECT ?item ?itemLabel ?birth ?death ?cbdd WHERE {
  ?item wdt:P227 "<GND>".
  OPTIONAL { ?item wdt:P569 ?birth. }
  OPTIONAL { ?item wdt:P570 ?death. }
  OPTIONAL { ?item wdt:P10626 ?cbdd. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "de,en,mul". }
}
```

Buildings near the CbDD coordinates (WDQS only; note `Point(lng lat)`):

```sparql
SELECT ?item ?itemLabel ?dist ?cbdd WHERE {
  SERVICE wikibase:around {
    ?item wdt:P625 ?loc.
    bd:serviceParam wikibase:center "Point(<lng> <lat>)"^^geo:wktLiteral;
                    wikibase:radius "0.3";
                    wikibase:distance ?dist.
  }
  OPTIONAL { ?item wdt:P10626 ?cbdd. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "de,en,mul". }
}
ORDER BY ?dist
```

Works of a candidate person on Wikidata (to compare with the CbDD works):

```sparql
SELECT ?work ?workLabel ?inception ?locationLabel WHERE {
  VALUES ?p { wdt:P170 wdt:P88 wdt:P84 } ?work ?p wd:<QID>.
  OPTIONAL { ?work wdt:P571 ?inception. }
  OPTIONAL { ?work wdt:P276 ?location. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "de,en,mul". }
}
```
