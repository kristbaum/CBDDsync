# Agentic reconciliation of CbDD entities

The sync tool (`uv run sync.py`) lists CbDD entities without a Wikidata item
carrying their deckenmalerei.eu ID (P10626) in `missing/missing_<type>.csv`.
Many of them **do** have a Wikidata item, just without the ID. Your job:
find that item, prove it is the same entity, and write a batch that adds the
ID. You never create items here; entities with no matching item stay in the
report as "no match".

Supported types for now: **people** (`missing/missing_people.csv`, sType
`ACTOR_PERSON`) and **buildings** (`missing/missing_buildings.csv`, sType
`OBJECT_BUILDING`).

## Inputs

- The list to work on: a `missing_<type>.csv` (column `ID`), a range of it, or
  explicit CbDD IDs given by the user. Default batch size: **10 entities** per
  run unless the user says otherwise. Whole tables are feasible for buildings
  with the bulk script (565 buildings took one session: ~15 min fetching,
  then review in blocks of 40–60).
- `sources/entities.json`, `sources/relations.json`, `sources/query.csv`
  (CbDD dump and the current P10626 links). If they are missing, tell the user
  to run `uv run setup.py` and `uv run sync.py` first.
- Wikidata: use the Wikidata MCP tools if available, otherwise the public API
  and SPARQL endpoints (see "Wikidata lookups").

## Outputs

Up to three files per run in `agentic-reconcile/to_match/`, same base name
`<type>_<YYYY-MM-DD>` (add `_2`, `_3` … if it already exists). Write them with
`scripts/write_batch.py` (step 5), which also picks the base name and runs the
self-checks:

1. `<base>.qs`: QuickStatements 3.0 batch, V1 commands, one line per **confirmed**
   match:

   ```
   Q<matched item>	P10626	"<CbDD ID>"
   ```

   TAB-separated, QID first, the CbDD ID quoted. No `+` prefix (adding the
   same ID twice is then a no-op), no `CREATE`, nothing else. Only matches with
   confidence **high** go in here.
2. `<base>_repair.qs`: fixes for errors found **on Wikidata** along the way
   (see "Repairs"); only written if there are any. Every line is explained,
   numbered, in the report.
3. `<base>.md`: the report (format below), covering **every** entity of the
   run, including rejected and ambiguous ones, every repair, and the errors
   only CbDD can fix.

Never edit files in `missing/` or `existing/`; they are regenerated by
`sync.py`. Never commit or push the outputs unless the user asks.

## Workflow

### 1. Pick the entities and build dossiers

```bash
python3 agentic-reconcile/scripts/cbdd_context.py \
    --csv missing/missing_people.csv --limit 10 --skip-done
```

`--skip-done` drops IDs already present in any file in `to_match/`, so
consecutive runs continue where the last one stopped. Use `--offset` to pick
another slice, or pass IDs directly as arguments.

The dossier collects what the CbDD dump knows about each entity:

- **People:** name and alternative names, gender, GND ID, every work they are
  related to with the **role** (`PAINTERS`, `PLASTERERS`, `ARCHITECTS`,
  `COMMISSIONERS`, `TEMPLATE_PROVIDERS`, …), the work's dating, host building
  and place, an approximate activity period, co-workers (with their QIDs if
  they are on Wikidata), and passages of the CbDD articles that mention the
  person. The texts often give life dates ("Joseph Anton Reiser (1757–1805)"),
  origin ("einer Gammertinger Malerfamilie") or office ("Bauinspektor").
- **Buildings:** address, coordinates, dating, functions, condition,
  GND ID, Bildindex object number (→ P2092), the ensemble it belongs to, its
  rooms, the people involved, the CbDD summary text.

**Buildings in bulk:** for more than a handful of buildings, skip the
per-entity dossiers and run

```bash
python3 agentic-reconcile/scripts/building_candidates.py \
    --csv missing/missing_buildings.csv --limit 600 --skip-done > candidates.txt
```

(put `candidates.txt` in your scratch directory). It queries every building's
300 m surroundings once, resolves the GND/Bildindex numbers, fetches the
candidates' statements and caches everything in `agentic-reconcile/.cache/`
(re-runs are instant, interrupted runs resume). Each building gets a compact
block with the best candidates first, flagged `ID` (identifier match), `ADR`
(street address match), `CBDD=…` (already linked) and `↑Q…` (parent monument
of a numbered component item). Read it in blocks of 40–60 and decide each
building directly; look things up only where the block leaves a doubt. Run it
in the background and start reviewing the slices already cached.

**People in bulk:** the same for people:

```bash
python3 agentic-reconcile/scripts/people_candidates.py \
    --csv missing/missing_people.csv --limit 2000 --skip-done > candidates.txt
```

It searches every name variant ("Given Surname", first given name only,
"von" forms, Joseph/Josef …) in the Wikidata full text restricted to humans,
resolves the CbDD GND via `P227` and via the Wikidata link of the lobid
record, and fetches the candidates' dates, occupations, places and offices
(~45 minutes for 1 700 people, cached). Flags: `GND` (item has the CbDD GND),
`GND(lobid,no-P227)` (only the GND record links to the item: a P227 repair),
`NAME` (all tokens of a name variant are in a label or alias; loose, it also
fires on partial names), `LIFE+`/`LIFE~`/`LIFE-`/`LIFE?` (lifetime fits /
fits most works / contradicts / no dates), `SEX-`, `CBDD=…`. The lifetime
check counts a work as fitting if any year of its dating fits, because CbDD
datings often list the building's whole history ("1385-1835/42, 1944/45");
`LIFE-` on a GND match is therefore usually a dating artefact (restorers,
later residents, paintings bought for a collection), rarely a wrong identity.

If something in the dossier is unclear, read the raw records in
`sources/entities.json` / `sources/relations.json` (relations are stored in
both directions; `ID -> relTar` with `sType` as the role, e.g. a painting
`PAINTERS ->` a person).

### 2. Find candidates

Try the strongest key first and stop searching once it hits:

1. **GND ID** (people and buildings): an item with `P227` = the CbDD GND ID.
   This is the best key, but still verify it (step 3); CbDD has a few
   malformed GND values (wrong length, missing check digit).
2. **People:** search by name. CbDD writes "Surname, Given names"; search
   "Given Surname" and the surname alone, in German. Try spelling variants
   (Joseph/Josef, Johann/Joh., ph/f, Italian and Latin forms,
   "von"/"de"), and the alternative names. Look at every candidate that is a
   human (`P31 Q5`). If the label search finds nothing, try the full-text
   search (`list=search`, finds aliases and descriptions such as
   "10 Mar 1706 - 1750 Erlangen") and the GND via lobid
   (`https://lobid.org/gnd/search?q=preferredName:"<Surname, Given>" OR variantName:"<…>"&filter=type:Person&format=json`):
   GND variant names bridge spellings (CbDD "Mermos" = Wikidata "Mermoos"),
   and the GND biography often states the office ("40. Abt von Kaisheim"). A
   GND number found this way leads straight to the item via `P227`.
   Genealogy items (P1819, P2600) often have no dates as statements but carry
   them in the description and the full given names in the aliases; family
   links (P22/P25/P40) can confirm what the CbDD text says about spouse or
   children.
3. **Buildings:** search items within ~300 m of the coordinates, then by name
   and locality. CbDD names are "Locality, Building" ("Polling, ehem.
   Augustiner-Chorherrenstift, Studienseminar").

Use the co-workers and buildings that already have QIDs: a candidate whose
item links to them (e.g. it is the `P170` creator of a painting in the same
building, or its article names the same church) is a strong hint.

### 3. Check each candidate against the CbDD evidence

Fetch the candidate's statements and compare. Write down every check, passed
or failed; the report needs them.

**People**

| Check | Wikidata | CbDD evidence | Rule |
|---|---|---|---|
| Lifetime vs. works | `P569` birth, `P570` death, `P1317` floruit, `P2031`/`P2032` work period | dating of works in roles where the person must be alive | Born at least ~12 years before their first work (≈20 for architects/master builders); died no earlier than ~2 years before their last work. An artist on an 18th-century painting cannot be born after 1900. |
| Exempt roles | | `TEMPLATE_PROVIDERS`, `REFERENCE_PERSONS`, `DONORS` | Templates are often engravings decades or centuries older; depicted/referenced persons can be long dead. Do **not** apply the lifetime rule to these roles; instead the person should have lived *before* the work. |
| Commissioners | | `COMMISSIONERS` | Often nobles, abbots, abbesses, prince-bishops. They may have commissioned as minors (regency) or died before completion; allow more slack, but the office must fit the place and time (a prince-abbess of Buchau, an abbot of the monastery the work is in). |
| Occupation | `P106` | the role | `PAINTERS` → painter, fresco painter; `PLASTERERS` → stuccoist; `ARCHITECTS`/`BUILDERS` → architect, master builder; `SCULPTORS` → sculptor. A missing occupation is not a contradiction; an incompatible one is. |
| Place | `P19`, `P20`, `P937`, `P27` | places of work | Should be plausible: same region, or a known itinerant artist. A painter who never left Italy, working only in Bavaria per CbDD, is suspicious. |
| Gender | `P21` | `gender` | Must match. |
| Text facts | descriptions, sitelinks | CbDD text passages | Life dates, family, offices in the CbDD text must agree. |
| Already linked | `P10626` on the candidate | | If the candidate already has a **different** P10626, do not match: report it as a possible CbDD duplicate. |

**Buildings**

| Check | Wikidata | CbDD evidence | Rule |
|---|---|---|---|
| Location | `P625` | coordinates | Within ~300 m (large complexes more). |
| Locality | `P131`, `P281`, `P6375` | `addressLocality`, `addressZip`, `addressStreet` | Must agree. |
| Scope | `P31`, `P361`/`P527` | name, functions, "Part of", parts | Same *scope*: the CbDD building "Kloster X, Bibliothek" is not the Wikidata item for the whole monastery, and a church is not its monastery. If CbDD has the part and Wikidata only the whole, that is **no match**. |
| Identity over time | `P571`, `P576`, `P5816` | dating, condition | A destroyed and rebuilt building may have separate items for the old and new building; match the one CbDD describes (CbDD documents the baroque interiors). |
| Identifiers | `P227`, `P2092` (Bildindex object number, the digits of `obj…`), `P4244` (Bavarian monument ID) | normdata | Any matching identifier is strong evidence. |
| Already linked | `P10626` | | As for people. Also see `errors/duplicates.md`. |

**Building patterns seen in practice** (565-building run, 2026-10):

- **Churches** are the easy majority: a church item within ~10 m whose patron
  matches is high. Patron variants are the same patron: Laurentius = Lorenz,
  Johannes Baptist = Johannes der Täufer = Johann, Nikolai = Nikolaus,
  Inventio Crucis / Kreuzauffindung = Heilig Kreuz, Margareta = Margaretha =
  Margareth, Kastulus = Castulus, St. Pölten = St. Hippolyt. Check the CbDD
  alternative names; they often carry the Wikidata label ("Ramsachkircherl",
  "Maria im Tal"). A different patron at the same spot is a contradiction.
- **Town houses** match by address: the label ("Engelsgrube 66",
  "Am Markt 14 (Wismar)") or `P6375`. Compare street *and* number exactly;
  the neighbours of a house usually have items, the house itself often not
  (Lübeck, Lüneburg: most CbDD houses have no item yet → no match).
- **Bavarian monument items come in layers:** the monument item (label is the
  name or "Baudenkmal D-…", address in `P6375`) and numbered component items
  ("Pfarrhof Kirchplatz 8 … (D-1-81-122-26#1)", often a gate, wall or
  outbuilding) with `P361` → the monument. Match the monument item, not the
  component. Bodendenkmal items ("Bodendenkmal in …, #D-1-…") are never the
  building, but sit on the same spot: a church 85 m from the CbDD point whose
  Bodendenkmal is also 85 m away means the CbDD point is offset, not that the
  church is wrong.
- **Monasteries:** if CbDD has the whole complex ("ehem. Augustiner-
  Chorherrenstift", alt. name "Kloster X"), the monastery item with the
  dewiki article is the match; next to it there is often a Germania Sacra
  item ("Kloster in Deutschland", P31 Kloster + religiöse Gemeinschaft,
  QIDs around Q2897…–Q2898…) for the institution — not the one to pick. A
  single wing, library, church or chapel of the complex needs its own item.
- **Institution vs. building:** museums, courts, libraries and schools often
  have only an institution item (P31 Museum, Amtsgericht, Bibliothek). High
  only if the item is also typed as the building (e.g. Fachwerkhaus,
  Bauwerk, Gebäude) or names it ("Schwedenspeicher-Museum",
  "Stadtmuseum Einbeck" typed Fachwerkhaus); otherwise medium.
- **CbDD rooms disguised as buildings:** entries like "Fembohaus, Tanzsaal"
  or "Pellerhaus, Schönes Zimmer, heute im Stadtmuseum" are rooms; the house
  item is a scope mismatch → medium.
- **One Wikidata item, two CbDD entries** (double church upper/lower church,
  provostry palace + church in one item): neither goes in the batch; both
  medium.
- **CbDD normdata is not always the building's:** the GND can be the parish
  ("Pfarrei St. Georg"), the collection (Gemäldegalerie Düsseldorf), the
  town (Schorndorf), a namesake church elsewhere (Ehekirchen-Holzkirchen vs.
  Holzkirchen) or another building of the same complex (Sanssouci for the
  Lordmarschallhaus). The bulk script prints the GND's own name from lobid;
  compare it before trusting an ID hit or a missing one.
- **CbDD coordinates are sometimes far off** (Duttenstein points 6.5 km away
  at Schloss Taxis; Weilheim St. Pölten points at the parish office). If no
  candidate fits, search by name before deciding "no match".

### 4. Decide

- **high**: a matching GND (or Bildindex) ID with no contradiction, **or** at
  least two independent agreeing hints (e.g. name + lifetime fits the works +
  occupation; coordinates + name + locality) with no contradiction, and no
  second candidate that fits as well. → `.qs` line and report.
- **medium**: plausible but thin (name and period fit, nothing else
  confirms), or two candidates not fully separable. → report only, with what
  would settle it.
- **no match**: no candidate, or all candidates contradicted. → report only.

One contradiction (wrong lifetime, wrong gender, different P10626, wrong
scope) rules a candidate out, however good the name match. Never put two CbDD
IDs on the same QID in one batch, and never one CbDD ID on two QIDs. If both
come up, downgrade them to medium and explain.

Do not guess. Every claim in the report must come from the dossier, the
source JSON, or a statement/page you actually looked up.

Record each decision as you go in a decisions file (JSON, in your scratch
directory; format in the docstring of `scripts/write_batch.py`): one entry per
entity with `decision`, `qid`, `evidence` (and `rejected`), plus `repairs`,
`cbdd_corrections` and `notes` as you find them. Writing the decision down
right after reviewing a block keeps long runs consistent and makes step 5 a
single command. Collect items you want to look up later (a parent monument, a
name search after an offset point) and resolve them in one go per block.

### 5. Write the files

```bash
python3 agentic-reconcile/scripts/write_batch.py <scratch>/decisions.json
```

It writes `<base>.qs`, `<base>_repair.qs` (if there are repairs) and
`<base>.md`, after checking:

- every `.qs` line is `Q…<TAB>P10626<TAB>"<UUID>"`, from a **high** entry;
- no QID and no UUID occurs twice (two CbDD IDs on one item → it refuses;
  downgrade both to medium);
- every entity is decided exactly once;
- live on Wikidata: none of the matched items has a P10626 by now
  (`sources/query.csv` may be stale), no item is missing or redirected, every
  `-` repair still finds its value.

If it refuses, fix the decisions file and run it again; it writes nothing
until all checks pass. `--offline` skips the live checks (only for drafts).

Finish with a short summary to the user: counts per decision, number of
repairs, and the file paths. Do not run the batches; the user reviews and
runs them.

## Repairs (`<base>_repair.qs`)

While checking candidates you meet errors. Sort each one into the place where
it can be fixed, and explain every one in the report:

| Found | Where it goes |
|---|---|
| Matched item lacks the building's/person's GND that CbDD has, and lobid confirms the GND names the same entity | repair: `Q…<TAB>P227<TAB>"<GND>"` with the CbDD reference |
| Matched item lacks the CbDD Bildindex number (`obj…` digits) and no other item has it | repair: `Q…<TAB>P2092<TAB>"<digits>"` with the CbDD reference |
| Malformed value on Wikidata, e.g. a P10626 that is not a UUID (`"cbdd10059"`) next to the valid one | repair: `-Q…<TAB>P10626<TAB>"cbdd10059"` |
| A Wikidata statement that is demonstrably wrong (identifier of another building, wrong P131) | repair: `-` line for the wrong value (plus the correct value if known) |
| Two Wikidata items for the same building | report only (`notes`): merging is not reversible by batch; the user merges via Special:MergeItems |
| Item already carries another CbDD ID (CbDD duplicate) | report only (`cbdd_corrections`) |
| Wrong or malformed GND/Bildindex in CbDD, offset coordinates, wrong address, two CbDD records for one building | report only (`cbdd_corrections`) |

Rules:

- Repairs touch only statements you have verified; when in doubt, put the
  case in the notes instead.
- Additions get the reference `S248 Q107174967` (stated in: CbDD) and
  `S10626 "<CbDD ID>"`, like the statement batches of `sync.py`; set
  `cbdd` in the repair entry and `write_batch.py` adds it. Removals (`-`)
  carry no reference.
- Adding a value an item already has is harmless (the reference is merged);
  an item may have two GNDs for the same building (old and new records).
- Repairs are independent of the match batch: they may concern items that
  are only medium or that block a match (e.g. the duplicate).

## Report format (`<base>.md`)

`write_batch.py` renders this from the decisions file. For people, put the
evidence table into `evidence`; for buildings in bulk a single evidence line
is enough ("address Große Messergasse 6 (P6375); 11 m; 2. Hälfte 17. Jh.
fits CbDD ab 1679"). The structure:

```markdown
# CbDD → Wikidata matches: <type>, <date>

Input: `missing/missing_<type>.csv`, rows <offset>–<offset+n> (or: IDs given by the user).
Batch: `<base>.qs`, <n> commands. High: <n>, medium: <n>, no match: <n>.

## Matched (high)

### <CbDD name> → <Wikidata label> (Q…)

CbDD: https://www.deckenmalerei.eu/<ID> · Wikidata: https://www.wikidata.org/wiki/Q…

| Evidence | CbDD | Wikidata | Result |
|---|---|---|---|
| GND | <GND> | P227 <GND> | match |
| Lifetime vs. works | PAINTERS, works 1776–1790 | P569 1757, P570 1805 | fits |
| Occupation | PAINTERS | P106 painter | fits |
| Place | Gammertingen, Bad Buchau | P19 <place> | fits |
| CbDD text | "… (1757–1805) … einer Gammertinger Malerfamilie" | | agrees |

Rejected candidates: Q… (born 1902, after the works).

## Uncertain (medium), not in the batch

### <CbDD name>
Candidates: Q… (why it fits, what is missing), Q… (…).
Would settle it: …

## No match

- <CbDD name> (<ID>): searched "…", "…"; candidates Q… (rejected: …). Probably no item yet.

## Repairs (`<base>_repair.qs`)

1. `Q20266684 ⇥ P227 ⇥ "4821135-7" ⇥ S248 ⇥ Q107174967 ⇥ S10626 ⇥ "<ID>"` — GND of the church (lobid: "Sankt Jakobus der Ältere (Mammendorf)"), missing on the item.

## CbDD corrections (not fixable via QuickStatements)

- <CbDD name> (<ID>): GND 4132604-0 is Schloss Sanssouci, not this house.

## Notes

- Wikidata duplicates to merge, other observations.
```

Leave out empty sections.

## Wikidata lookups

With the Wikidata MCP server: `search_items` for names, `get_statements` for a
candidate, `execute_sparql` for the queries below. Without it, use the HTTP
endpoints and send a descriptive `User-Agent`:

- Name search: `https://www.wikidata.org/w/api.php?action=wbsearchentities&search=<name>&language=de&uselang=de&type=item&limit=20&format=json`
- Exact identifier: `https://www.wikidata.org/w/api.php?action=query&list=search&srsearch=haswbstatement:P227=<GND>&format=json`
- Full item: `https://www.wikidata.org/wiki/Special:EntityData/<QID>.json`
- SPARQL: `https://query.wikidata.org/sparql?format=json&query=…` (WDQS; needed
  for `wikibase:around`). QLever (`https://qlever.dev/api/wikidata`) is
  faster for plain lookups but has no label or geo services.
- Many items at once: `wbgetentities` with up to 50 `ids=Q1|Q2|…` per call is
  far faster than one SPARQL query per item.

Practical notes: WDQS answers 502/429 now and then; retry with a pause
(the scripts do). Keep `wikibase:around` queries to `?item ?dist` and fetch
statements separately — adding OPTIONALs for several properties multiplies
the rows (13 MB for 300 buildings). Label `CONTAINS` filters over all humans
time out on both endpoints; use the search APIs instead. The Wikidata MCP
server's own instructions warn that its IDs may differ from the live ones,
so take QIDs for the batches from the public API, not from MCP output.

People with this GND, with dates and any existing CbDD ID:

```sparql
SELECT ?item ?itemLabel ?birth ?death ?cbdd WHERE {
  ?item wdt:P227 "<GND>".
  OPTIONAL { ?item wdt:P569 ?birth. }
  OPTIONAL { ?item wdt:P570 ?death. }
  OPTIONAL { ?item wdt:P10626 ?cbdd. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "de,en,mul". }
}
```

Buildings near the CbDD coordinates (WDQS only; note `Point(lng lat)`):

```sparql
SELECT ?item ?itemLabel ?dist ?cbdd WHERE {
  SERVICE wikibase:around {
    ?item wdt:P625 ?loc.
    bd:serviceParam wikibase:center "Point(<lng> <lat>)"^^geo:wktLiteral;
                    wikibase:radius "0.3";
                    wikibase:distance ?dist.
  }
  OPTIONAL { ?item wdt:P10626 ?cbdd. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "de,en,mul". }
}
ORDER BY ?dist
```

Works of a candidate person on Wikidata (to compare with the CbDD works):

```sparql
SELECT ?work ?workLabel ?inception ?locationLabel WHERE {
  VALUES ?p { wdt:P170 wdt:P88 wdt:P84 } ?work ?p wd:<QID>.
  OPTIONAL { ?work wdt:P571 ?inception. }
  OPTIONAL { ?work wdt:P276 ?location. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "de,en,mul". }
}
```

## Fixed IDs

| What | ID |
|---|---|
| deckenmalerei.eu ID | `P10626` |
| GND ID | `P227` |
| Bildindex object number (CbDD `normdata.bildindex`, digits only) | `P2092` |
| Bavarian monument authority ID | `P4244` |
| human | `Q5` |
| male / female | `Q6581097` / `Q6581072` |
